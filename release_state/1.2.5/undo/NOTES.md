<summary>Decisions and why</summary>

- Greg (2026-11-26), after hand-checking the drag: "the app really really needs an undo/rollback. The user needs to be able to experiment, and the drag and drop quickly leaves them confused about where they were, with no good way to return." Pulled from `release_state/backlog.md` (line of 2026-11-16) into 1.2.5 and made ACTIVE; Access Analyzer set to Waiting on Greg.
- Greg's answers (2026-11-26):
  - **Both kinds:** step-by-step undo, several steps, plus a rollback that returns to an earlier point in one go (e.g. "before I started dragging"). One change log serves both.
  - **All section changes:** grid drags, right-click edits, section card Applies, and creating, deleting and copying sections. Not instructors, rooms, courses, commitments, notes or settings.
  - ~~Undoable after a save, until the app closes~~: superseded the same day (next bullets). It gave "saved" two meanings and needed explaining.
- **Save is the line (Greg, 2026-11-26).** Keep the "editing a file, saving a file" model: undo and rollback reach back only to the last save, so they invite experimenting as editing without saving does. Why: a Rollback button that works after a Save needs educating ("can I roll back a save? when do colleagues see it?").
- **Autosave to the shared file is dropped** (Greg: "a price worth paying"). Every edit already lands in D' at once; autosave only copied D' to D. Now only Save, and the close question, write the shared file. This folds in backlog 2.1 (experimenting without saving); one decision gives an easy rollback, experiments colleagues don't see, and a normal close.
- **Closing with unsaved changes asks Save / Don't save / Cancel**, the usual question, replacing today's silent save on close.
- **A deliberate Don't save is the user's choice** (Greg: "keep the simple model everyone knows"): rule 3 does not require keeping the thrown-away work, so the recovery redesign (3.5) need not come first.
- **Cost accepted:** after a lost lock (Bob sleeps, Alice takes over) Bob's kept changes are everything since his last Save, not 10 minutes at most. Nothing is lost: today's banner says they are kept and offered back, or can be saved as a separate copy if Alice changed the database first. Ideas to shrink it, for the design: an unsaved-changes marker, a nudge after a long stretch unsaved, warning Alice before a takeover.
- **Design drafted (Claude, 2026-11-26), awaiting Greg.** Choices made there and why:
  - Throw away = undo every *section* step back to the save (the history's last line); everything = Don't Save at close. Rejected: a "revert to saved" from a local copy of the last save. It would need a new copy kept at checkout and each save, a connection close and file swap under the live session (a new lock/save-path piece with its own cascade), and a whole-app reload, for little gain: experiments are section changes.
  - Fail-safe triggers: a section write that isn't a labelled step, or a delete in any other table, empties the history. A path the design missed can only shorten the history, never undo wrongly. Triggers on the other tables are generated from `sqlite_master`, so new tables are covered.
  - "Unsaved" = steps, or "other changes" (insert/update elsewhere), or "history incomplete". Undoing everything clears the line and the close question but never deletes the dirty marker (the bytes differ, catch 2); at close, "nothing unsaved" with a marker releases with a save, which writes nothing new for colleagues. No new marker-deletion path, so rule 3 rests on today's code.
  - Redo recommended: cheap with the same log, and it makes a multi-step jump safe without a confirmation.
  - `MinimumVersionToWrite` proposed No: undo writes back rows this version already writes; the log is TEMP.
  - The takeover question already warns Alice that Bob's unsaved changes can only go into a separate copy (`StaleLockPrompt`), so no lock-file change is proposed; the lost-lock cost is shrunk by the time on the unsaved line and a two-hour notice.
- **Greg approved the design and wording (2026-11-26), except decision 5.** His concern: an "Undo" that silently stops working because of unrelated work. The draft cut the history at any delete in another table, a semester copy or an import, and ordinary work deletes rows (editing legal start times deletes and re-inserts; commitments, notes, meetings and releases are deleted routinely). **Revised the same day:** other tables' triggers only set "other changes"; cleanup writes (deleting a room, type, tag, resource or reserve), Copy Semester, Import Sections and semester or academic-year deletes run with recording paused. At undo, references to anything deleted since are left out (one helper shared with the deletes' cleanup) and the line names them; a section whose course or semester is gone stays deleted. The fail-safe cut remains only for a section write that is neither a step nor paused. Approved by Greg the same day ("Approve, start build").
- **Changed behaviour needs education at release:** a "What's new" line, wording for Greg. An autosave setting kept for those who want it: Claude's advice is to leave it out unless asked.
- Checked 2026-11-26: D' is written through one long-lived connection, closed only on a lost lock (demotion), a reader refresh or a database switch (a new context). So the backlog's approach (SQLite TEMP triggers writing to a TEMP log table, which never reach D' or the shared file) would clear itself at exactly the moments the history must clear. Probed the same day (step 1): it holds, with two catches (Technical issues, "Probe results").

<summary>Technical issues</summary>

- **Probe results (step 1, 2026-11-26).** The probe (10 tests, since folded into `SectionChangeLogTests`) ran a TEMP log table plus three TEMP triggers on `main.Sections` against the real `DatabaseContext` and the save's real snapshot (`SnapshotWorkingCopy`, by reflection). Its guarantees are now tested against the real implementation.
  - Never reaches the shared file: the snapshot's content fingerprint is identical with and without the log (also after the same edits on a twin without it); no trigger or log table in the snapshot's or D''s schema.
  - Emptying the log at a save is not an edit to the save: `PRAGMA data_version` on the save's snapshot connection does not change (a real edit does).
  - A log entry commits and rolls back with the repository write that made it (same transaction).
  - Gone after `ReinitializeConnection` (read-only or not) and after a new context on the same path (switch, with or without `CloseConnection`).
  - Exact rows: writing old rows back (newest first, triggers paused by a TEMP flag table) restores every column of every row, including meetings and a JSON field from a newer version. Plain `INSERT`/`UPDATE`/`DELETE` in `SectionRepository` (no `REPLACE`), so the delete trigger sees every lost row.
  - **Catch 1: pooling.** A pooled connection hands its TEMP tables to the next opener of the same connection string unless `SqliteConnection.ClearAllPools()` runs. All three close paths in `DatabaseContext` clear the pool today; that must stay, and creating the log should start empty (drop or empty it first) as a second guard.
  - **Catch 2: bytes.** After throwing everything away from the log, the rows are exact but the file's content fingerprint differs from the start (page layout). So the save's "nothing changed" skip (`ContentHashAtCheckout`) won't fire, and neither the fingerprint nor the dirty marker can tell "no unsaved changes". Design choice for step 3: "throw away" restores D' from a local copy of the last-saved state (bytes identical; also throws away non-section edits, like "revert to saved"), or the app tracks "unsaved" itself (log empty plus no other edit since the save) and removes the dirty marker when nothing is left.
  - Side facts: a read-only session (`query_only` on) refuses to create the log (SQLITE_READONLY, 8), so create it only on writer opens: the constructor and `ReinitializeConnection(readOnly: false)`. `temp_store` is the default (0); `PRAGMA temp_store=MEMORY` would keep the log off disk.
- **Section write paths (step 2).** Every section write goes through `SectionRepository` (`Insert`, `Update`, `Delete`, `DeleteBySemesterId`); the triggers see them all, so the design must say which ones are undo steps.
  - Undoable (Greg's list): grid drop, `ScheduleGridViewModel.CommitMeetingDrag` (one `Update`, also Alt group drags; then `ReloadSectionStore` and select). Grid right-click instructors, room, tags, flag: `SectionContextMenuViewModel.Confirm` (one `Update`; then `ReloadSectionStore`). Card Apply for add, edit and copy: `SectionListViewModel.CreateEditVm` `onSave` (`Insert` or `Update`; collapse, `SectionStore.Reload`, refresh the card or rebuild). Delete: `SectionListViewModel.Delete` (confirm, `Delete`, `SectionStore.Reload`). Pins and "Don't suggest moving this" in the right-click menu write no section.
  - Section writes caused by other edits (not on Greg's list): course "apply tags to all sections" (`CourseListViewModel.ApplyTagsToAllSections`, one `Update` per section, no transaction); room delete clears it from meetings (`RoomListViewModel`, one transaction with the room delete); deleting a section type, delivery type, reserve or meeting type clears it from sections (`SchedulingEnvironmentListViewModel`, one transaction); copy semester (`CopySemesterViewModel`, inserts in a transaction); Files > Import Sections (`SectionImportWriter`, in a transaction); semester or academic-year delete (`SemesterContentsService`, `DeleteBySemesterId`). Migrations write sections before the log exists. Undoing a section change past one of these could bring back a reference to a deleted room, type or semester: the design must make them barriers (history before them can't be undone) or log every table.
  - Every undo would reload `SectionStore`, which closes an open card: check `OpenCardMessages.WhyRefused` first, as the grid does.
- **Saves the user didn't ask for (step 2).** Each must become the close question or be rethought.
  - Autosave timer: `CheckoutService.StartAutoSave`/`AutoSaveTickAsync` (~line 4269), started at startup (`MainWindow.axaml.cs` ~line 736), by the setting's toggle (`MainWindowViewModel` ~line 333) and interval (`SaveAndBackupViewModel` ~line 47), and resumed after a restore that didn't start (`SessionLifecycle.ResumeAutoSave` ~line 1865). The setting's UI goes too (an AXAML edit: warn Greg).
  - Exit: `SessionLifecycle.TeardownForCloseAsync` → `ReleaseAsync(saveFirst: wasWriteMode)` (~line 1634).
  - Database switch, including File > Open and a reader taking write access: `SwitchCoreAsync` → `ReleaseAsync(saveFirst: …)` (~line 1006). Already preceded by the card's "Unapplied Changes" question (`ResolveUnappliedChangesAsync`); the close question must not make that two questions for one close (rule 4). That question is asked at close (`MainWindow.OnClosing`) and switch only, not before a restore: check in the build how an open card behaves during a restore.
  - Restore from backup: `SaveThenRestoreAsync` saves first (~line 1821).
  - Crash recovery: `SaveRestoredChangesAsync` saves restored changes at once (~line 270). Under "Save is the line", leave them unsaved for the user instead? (They come back as one lump with no undo steps: the log is TEMP.)
  - Not saves: a lost lock keeps D' (no save); `ResetAfterFailedOpenAsync` and the post-restore teardown release with `saveFirst: false`; the manual Save is `MainWindowViewModel` ~line 351.
- After throwing everything away, D' matches D again: the dirty marker and edit counter must say "no unsaved changes", or the close question would ask with nothing to save (and see Catch 2 above).
- Periodic backups copy D', so with no autosave they will hold unsaved experiments for longer: check in step 3 whether that matters (where they go, what a restore of one means).
- Risks to carry into the design (from the earlier costing): an undo must refuse when the section has changed since the step (e.g. edited in its card); undoing writes from outside the card needs the `OpenCardMessages` guard, since the reload closes an open card; re-inserting a deleted section must keep its id, its meetings and its extension data (`WithExtensionDataFrom`, `SectionDaySchedule.Clone()`).
- Found in passing (2026-11-26, not part of undo): deleting or editing a room (`RoomListViewModel` Delete and Edit's `onSave`) reloads the Section List without the `OpenCardMessages.WhyRefused` check the environment-value delete has, so an open section card would close and lose what was typed (CLAUDE.md gotcha). Not fixed; for Greg to place.
- Writing old rows back through raw SQL would bypass the repositories and stores: the stores must reload, and the edit counter (`NoteEdit`) and dirty marker must see the undo as an edit, or the next save would skip it.
